# 栄養素推計ツール 要件定義書

## 1. 文書情報

- 文書名: 栄養素推計ツール 要件定義書
- ファイル名: `docs/features/nutrient_estimate.md`
- 対象システム: NutritionApp連携用 栄養素欠損補完ツール
- 位置付け: NutritionAppのMVP完成後に利用できる任意拡張
- 想定利用環境:
  - NutritionApp: PWA
  - クライアント保存領域: IndexedDB
  - 推計コア: ブラウザ内処理（本番用）とPython（検証・再現用）
  - 開発環境: macOS / Visual Studio Code
- 検証対象栄養素:
  - 飽和脂肪酸
  - 食物繊維
  - カルシウム
  - 鉄
  - ビタミンA
  - ビタミンE
  - ビタミンB1
  - ビタミンB2
  - ビタミンC

### 1.1 正本との関係

- NutritionApp全体の要件の正本は [`../requirements.md`](../requirements.md) とする。
- 本書と正本が矛盾する場合は正本を優先する。本書は正本のMVP範囲、完成条件、データ保全、プライバシー、UI方針を変更しない。
- 本機能は正本のMVP受け入れ条件および完成判定に含めない。既存MVPを完成させた後に着手し、MVPの入力速度、オフライン利用、バックアップ・復元を損なわないことを着手条件とする。
- 本書に記載するフィールド、IndexedDBストア、画面およびPython検証用コアは実装済みの契約として扱い、変更時は正本要件と設計判断を確認する。
- 常時稼働するバックエンドはNutritionAppの必須構成にしない。外部サービスを利用しない場合も、NutritionAppの既存機能はすべて継続利用できること。

---

## 2. 背景

NutritionAppは、JANコードを利用して食品情報を取得し、食品データをIndexedDBへ保存するPWAとして開発している。本書は実装の完成度を前提にせず、正本のMVP完成後に追加する機能だけを定義する。

Open Food Factsなどの外部データソースから取得した食品情報には、エネルギー、たんぱく質、脂質、炭水化物、食塩相当量などの基本栄養素が含まれる一方、飽和脂肪酸、食物繊維、ビタミン、ミネラルなどが欠損している場合がある。

本ツールは、JANコード、商品名、メーカー、原材料表示、公表済み栄養成分などを用いて欠損栄養素を推計し、NutritionApp上でユーザーに参考候補として提示する。市販品はパッケージの栄養成分表示またはユーザー入力を正とし、外部データと推計値は補助情報として明確に区別する。ユーザーは栄養素ごとに採用または不採用を選択し、採用した値だけを食品マスターへ反映する。

---

## 3. 目的

本ツールの目的は以下とする。

1. NutritionApp内の食品データに存在する栄養素の欠損を補完する。
2. 推計値を既知値と区別して管理する。
3. 単一の確定値だけでなく、推定範囲、信頼度、警告を提示する。
4. NutritionAppへ依存しない独立した推計コアを構築する。
5. 将来的に複数の食品カテゴリへ拡張可能な構造を採用する。
6. 初期実装では対象カテゴリを限定し、精度検証を優先する。

---

## 4. 基本方針

### 4.1 システム構成方針

- NutritionAppとの連携を前提として入出力インターフェースを先に定義する。
- 推計コアはNutritionApp、IndexedDB、UI、JAN読み取り処理へ直接依存しない。
- NutritionApp固有JSONと推計コアの共通入力形式の間にアダプターを設ける。
- 推計結果は既存値を直接上書きせず、採用操作後に反映する。
- 推計値の由来、モデルバージョン、信頼度、推定範囲を保持する。
- 推計の自動実行を設定で許可しても、自動採用は行わない。自動採用を将来検討する場合は、先に正本の要件変更とデータ保全・精度・誤採用リスクの再評価を行う。
- 数値が既に存在する栄養素を推計値で上書きしない。メーカー公表値、パッケージ表示、ユーザー入力を推計値より優先する。
- 推計値の採用は食品マスターの将来の利用にだけ反映し、保存済み食事記録の食品・栄養スナップショットと集計値を変更しない。

### 4.2 開発方針

- アーキテクチャは複数カテゴリ対応を想定する。
- 初期実装・検証は単一カテゴリに限定する。
- カテゴリ固有ルールをコード内の大量の条件分岐として実装しない。
- 配合範囲、候補原材料、加工係数などは設定データとして管理する。
- 最初の対象候補はクッキー・ビスケット類とする。

## 8. 機能要件

### EST-FR-001 欠損栄養素の検出

- NutritionAppは、`nutrients`内で値が`null`の栄養素を欠損として検出できること。
- 数値`0`と`null`を明確に区別すること。
- 推計対象外の欠損値は推計要求から除外できること。

### EST-FR-002 推計の起動方式

ユーザー設定により、以下を選択できること。

- 手動実行
- JAN取得後の自動実行
- 推計機能を無効化

初期検証版で提供するのは手動実行と機能無効化だけとする。JAN取得後の自動実行はPhase 6の拡張とし、外部送信制約と既存の食品登録導線を検証してから追加すること。

自動実行は推計要求の作成までとし、推計値を食品マスターへ自動採用しないこと。外部API型の場合は、正本のプライバシー要件に従ってバーコード以外を送信せずに実行できる場合に限ること。

初期既定値は以下とする。

```json
{
  "enabled": false,
  "trigger": "manual",
  "applyMode": "manual"
}
```

### EST-FR-003 推計専用入力の生成

NutritionAppの食品JSONを推計専用入力形式へ変換できること。

共通入力項目:

- `requestId`
- `foodId`
- `barcode`（JAN/GTINを持つ場合）
- `name`
- `maker`
- `estimatorCategoryId`（推計用カテゴリへ分類済みの場合。NutritionAppの`foodGroupId`とは別に管理する）
- `baseAmount`
- `baseUnit`
- `inputUnitConversions`
- `referenceMassG`
- `referenceMassSource`
- `knownNutrients`
- `missingNutrients`
- `ingredientsText`
- `ingredientsSource`
- `requestedAt`
- `inputHash`

JAN/GTINは文字列として扱い、先頭ゼロを保持すること。`knownNutrients`の値は`baseAmount`と`baseUnit`に対応する保存値であり、推計入力のために暗黙に100 g当たりへ変換しないこと。

`referenceMassG`は、製品基準量に対応する可食部または内容物の質量を、パッケージ表示等の根拠から明示できる場合だけ設定する。`個`、`袋`、`ml`等からgへの換算を推測しないこと。質量基準の配合最適化に必要な換算がない場合は、推計不可または当該方式を使用しない結果を返すこと。

### EST-FR-004 原材料情報の取得元

原材料情報は以下の優先順位で利用できる設計とする。

1. パッケージを確認してユーザーがNutritionAppへ入力・確認した原材料表示
2. NutritionApp内に保存済みの、取得元を確認できる原材料表示
3. Open Food Factsなど、利用条件を確認済みの外部商品DBから取得してユーザーが確認した値
4. 利用許諾、出典、更新条件を確認済みの業務用商品DB
5. 将来的なOCR入力

原材料情報が存在せず、根拠を定義した代替推計方式もない場合は`unavailable`とすること。カテゴリ統計等による代替推計を行う場合だけ、使用した方式と根拠を表示して`low`として扱えること。

外部データは補助情報とし、取得元、取得日時、注意事項を表示してユーザー確認後に保存すること。利用条件を確認できない第三者DBのスクレイピング、同梱または再配布を行わないこと。

### EST-FR-005 原材料文字列の保存

以下を分離して保存すること。

- 原文
- 正規化後名称
- 括弧内情報
- 原産国・製造地情報
- アレルゲン情報
- 添加物区分
- 複合原材料情報

例:

```json
{
  "rawName": "小麦粉（国内製造）",
  "normalizedName": "小麦粉",
  "originNote": "国内製造",
  "allergens": ["小麦"]
}
```

### EST-FR-006 原材料表示順制約

- 原材料は原則として重量順に並ぶものとして扱うこと。
- 最適化時に以下の制約を設定できること。

```text
ingredient_1 >= ingredient_2 >= ... >= ingredient_n
```

- 表示規則の例外や同率の可能性を考慮し、厳密制約と緩和制約を切り替えられること。

### EST-FR-007 原材料候補の解決

曖昧な原材料名に対して複数候補を保持できること。

例:

```text
植物油脂
  ├─ なたね油
  ├─ 大豆油
  ├─ パーム油
  └─ 混合油脂
```

候補ごとに以下を保持できること。

- 対応食品ID
- 事前確率
- 食品カテゴリ条件
- 最小配合率
- 最大配合率
- 信頼度
- 根拠または出典

候補の優先順位は、原材料表示の明示語を最も強く、入力済み主要栄養値との整合を次に強く、商品名および商品名から推測するカテゴリを弱い事前確率として扱うこと。例えば`なたね油`という明示語は商品名より優先し、`植物油脂`のように油種が不明な場合だけ商品名を補助的に使う。商品名事前確率は学習済み・校正済みの確率と誤認させず、使用時は低信頼度と警告を付けること。

原材料表示は次の境界を区別すること。

- 最上位の`／`または`/`以降は添加物区画として主原材料の配合順から分離する。
- `／`がない場合は既知の添加物名を補助境界にできるが、推定したことを警告する。
- `ゆず砂糖漬け（ゆず、砂糖）`のような複合原材料は、外側の重量順と括弧内の重量順を別々に保持する。
- `小麦粉（国内製造）`、`バター（乳成分を含む）`等の産地・製造地・アレルゲン注記は構成原材料へ展開しない。
- 閉じ括弧がない等の不正な表記は、推測で分解せず未対応として扱う。

これらの境界は、消費者庁の[食品添加物表示に関するマメ知識](https://www.caa.go.jp/policies/policy/food_labeling/food_sanitation/food_additive/assets/food_labeling_cms204_210408_01.pdf)および[食品表示基準Q&A](https://www.caa.go.jp/policies/policy/food_labeling/food_labeling_act/pdf/food_labeling_act_180921_0024.pdf)の表示例を根拠とする。

### EST-FR-008 工業用原材料マスター

栄養管理用食品DBとは別に、工業向けの原材料レイヤーを追加すること。

最低限の項目:

- `ingredientId`
- `canonicalName`
- `ingredientType`
- `ingredientGroup`
- `industrialRole`
- `typicalMinRatio`
- `typicalMaxRatio`
- `categoryConditions`
- `notes`

`ingredientType`は以下を想定する。

- `single`
- `compound`
- `additive`
- `ambiguous`

### EST-FR-009 既存食品DBの再利用

既存のNutritionApp用食品DBを共通栄養成分コアとして再利用すること。

共通化対象:

- 食品
- 栄養素
- 食品別栄養値
- 単位
- 出典

工業推計用に分離する対象:

- 原材料表示語
- 原材料候補
- 食品カテゴリ別事前分布
- 配合範囲
- 加工係数
- 複合原材料
- 表示ルール
- 推計信頼度ルール

### EST-FR-010 栄養成分データの品質要件

食品成分DBは以下を満たすこと。

- 元データの基準量・基準単位を保持すること。MEXT食品は出典どおり可食部100 g当たりを維持し、市販品はパッケージ表示の「1個当たり」「1袋当たり」「100 g当たり」等を維持すること。
- 推計コア内部で100 g当たりへ正規化する場合は、対応する可食部重量または内容物重量の明示的な換算根拠があるデータだけを対象とすること。
- g、ml、個、袋等を混同せず、変換根拠がない値を推測で換算しないこと。
- 栄養素単位が統一されていること。
- 食品IDが安定していること。
- 出典が保存されていること。
- 調理前後を区別できること。
- 水分状態を区別できること。
- 欠損値とゼロを区別できること。
- ユーザー提供または事前検証済みDBは、元ファイルを直接利用せず、再生成可能な検証・正規化処理を通した生成物だけを使用すること。

### EST-FR-011 配合量最適化

既知栄養値に一致または近似するよう、原材料配合量を推定できること。

使用候補:

- `scipy.optimize`
- `cvxpy`
- `OR-Tools`

最適化では以下を考慮すること。

- 原材料量合計
- 原材料表示順
- 公表済み栄養値
- 食品カテゴリ別配合範囲
- 原材料ごとの通常使用量
- 栄養寄与の有無
- エネルギー整合性
- 水分収支
- 加工による重量変化

### EST-FR-012 推計対象栄養素

検証版は、NutritionAppが保持する以下の欠損栄養素を推計対象とする。

- `saturatedFatG`
- `fiberG`
- `calciumMg`
- `ironMg`
- `vitaminAMcg`
- `vitaminEMg`
- `vitaminB1Mg`
- `vitaminB2Mg`
- `vitaminCMg`

### EST-FR-013 加工・調理係数

食品カテゴリおよび栄養素ごとに、加工損失・残存率を設定できること。

例:

- 加熱によるビタミンC損失
- 焼成による水分減少
- 油吸収率
- 濃縮・乾燥による重量変化

初期版では、加工係数が未整備の場合に警告を返すこと。

### EST-FR-014 推定範囲の算出

単一の推定値だけでなく、以下を出力すること。

- 中央推定値
- 最小推定値
- 最大推定値
- または指定パーセンタイル範囲

将来的には、候補原材料、配合範囲、加工係数を変化させるモンテカルロ法または複数シナリオ最適化に対応すること。

### EST-FR-015 信頼度の算出

各栄養素について以下の信頼度を返すこと。

- `high`
- `medium`
- `low`
- `unavailable`

信頼度の判定には以下を考慮すること。

- 原材料表示の有無
- 原材料候補の曖昧さ
- 既知栄養値の数
- 最適化誤差
- 複数シナリオ間の分散
- 加工係数の有無
- メーカー公表値との整合性
- 食品カテゴリ適合度

### EST-FR-016 警告生成

以下のような警告を返せること。

- 原材料表示が存在しない
- 植物油脂の種類を特定できない
- 複合原材料の詳細が不明
- 最適化誤差が大きい
- 食品カテゴリが未対応
- 加工係数が未定義
- 推計範囲が広い
- 栄養成分表示とエネルギー値の整合性が低い

### EST-FR-017 推計結果の提示

NutritionApp上で以下を比較表示できること。

- 現在値
- 外部データソース取得値
- 推計値
- 推定範囲
- 信頼度
- 推計方法
- 警告
- モデルバージョン

推計値は「参考推計」と明記し、メーカー公表値、パッケージ表示、ユーザー入力および外部データ取得値と視覚的・文言上区別すること。推計値が医療上の判断、診断、治療または個別の栄養指導に使用できる精度を保証しないことを表示すること。

### EST-FR-018 採用・不採用

ユーザーは以下の操作を行えること。

- 栄養素単位の採用
- 栄養素単位の不採用
- 一括採用
- すべて不採用
- 採用後の取り消し

一括採用はユーザーが選択した欠損栄養素を1回の確認で保存する操作とし、未選択項目および既存値を変更しないこと。

### EST-FR-019 採用時の保存

- 採用前の推計値は`foods`ストアへ直接反映しないこと。
- 採用操作後に、現在値が`null`の栄養素だけを`nutrients`へ反映すること。
- 採用した値には栄養素単位のメタデータを付与すること。
- 既存値がある場合は採用不可とし、パッケージ表示またはユーザー入力を正として維持すること。
- 推計開始後に対象食品の入力値、原材料、基準量、単位または対象栄養素が変更されていた場合は採用を中止し、再推計を案内すること。
- 食品マスター、栄養素メタデータおよび採用判断履歴をIndexedDBの1トランザクションで保存し、一部だけを成功させないこと。
- 保存の完了または失敗を日本語で明確に通知し、失敗を成功扱いにしないこと。
- 採用後の取り消しは、採用時に保存した直前値とメタデータを復元すること。ただし採用後に対象食品が別操作で更新されている場合は自動復元せず、競合内容を表示すること。
- 食品マスターの採用または取り消しによって、既存の食事記録、料理メニュースナップショットまたは計算済み栄養値を更新しないこと。

### EST-FR-020 推計履歴

以下を保存できること。

- 推計要求
- 推計結果
- 採用・不採用判断
- 採用日時
- 推計モデルバージョン
- 入力データのハッシュまたはスナップショット
- 再推計履歴

履歴の日時はISO 8601で保存すること。履歴参照はIndexedDBのインデックスとページングを使用し、全履歴を無制限にメモリへ読み込まないこと。

### EST-FR-021 食事記録スナップショット

- 推計値を採用した食品を新たに食事へ登録する場合、登録時点の`nutrients`と`nutrientMetadata`を食品スナップショットへ保存すること。
- 採用前に保存済みの食事記録は、採用後も登録時点の食品名、基準量、入力単位換算、栄養値、計算済み栄養値を維持すること。
- 食品を削除しても食事記録を削除せず、削除済み食品として当時のスナップショットを表示できること。

### EST-FR-022 JSONバックアップ・復元とCSV

- 正本で定める食品、食事記録、設定、お気に入り、料理メニュー、メニューセットおよびアプリのデータ形式バージョンに加え、JSONバックアップには`nutrientMetadata`、原材料情報、推計設定、推計要求、推計結果、採用・不採用判断、推計関連データ形式バージョンを含めること。
- 復元前に現在データを自動退避し、形式、バージョン、必須項目、栄養素キー、単位および参照整合性を検証すること。不正ファイルでは既存データを変更しないこと。
- 復元方式の初期値は全置換とし、上書き警告を表示すること。復元はトランザクションで行い、中途半端な状態を作らないこと。
- CSVの正本で定めた初期列順を変更しないこと。推計由来を食事履歴とともに移送する場合は、既定列の後ろに食品スナップショットの`nutrientMetadata`を表す列を追加すること。
- 推計関連データを含む完全復元にはCSVではなくJSONバックアップを使用すること。

### EST-FR-023 スキーマとマイグレーション

- IndexedDBのスキーマにはバージョンを付け、現行ストアを維持したまま推計用ストアとフィールドを追加すること。
- マイグレーション、型定義、バックアップ検証および初期値を同じ変更で更新すること。
- 開発段階でも、作業範囲外の現行ユーザーデータを削除、移行または上書きしないこと。

## 13. 推計ロジック要件

### 13.1 基本モデル

原材料ごとの使用量を変数とし、既知栄養値との誤差を最小化する。

```text
minimize:
  既知栄養値との加重誤差
  + 配合事前分布からの逸脱
  + 非現実的配合へのペナルティ
```

制約例:

```text
原材料量合計 = 製品基準重量
原材料1 >= 原材料2 >= ... >= 原材料n
各原材料量 >= 0
カテゴリ別最小配合率 <= 原材料量 <= カテゴリ別最大配合率
```

`原材料量合計 = 製品基準重量`は、製品基準量に対応する`referenceMassG`とその出典を確認できる場合だけ使用すること。基準単位が`個`、`袋`、`ml`等で質量換算がない場合は重量を推測せず、このモデルによる推計を`unavailable`とすること。

推計結果は推計要求と同じ`baseAmount`・`baseUnit`に対応する値として返し、結果JSONにも基準量・基準単位を含めること。

### 13.2 目的関数

既知栄養値ごとにスケールが異なるため、正規化誤差または相対誤差を使用すること。

例:

```text
error = Σ weight_nutrient × ((estimated - target) / scale)^2
```

### 13.3 エネルギー整合性

- 公表エネルギーと主要栄養素から計算されるエネルギーの差を評価すること。
- 日本の栄養成分表示における丸め誤差を許容すること。
- エネルギー係数の差異を警告として扱えること。

### 13.4 複合原材料

初期版では以下のいずれかで扱う。

1. 代表食品として扱う
2. 既定レシピへ展開する
3. 複数候補シナリオを生成する

現行ブラウザ版は3を採用し、括弧内の原材料表示順を保った複数の内部配合候補を作る。括弧内の候補を解決できないが外側名称に参照食品がある場合だけ、外側名称を低信頼度の代替候補として比較する。

例:

```text
チョコレート
  ├─ 砂糖
  ├─ カカオマス
  ├─ ココアバター
  └─ 乳成分
```

### 13.5 栄養寄与の小さい原材料

香料、着色料などは以下のいずれかで扱えること。

- 最適化変数から除外
- 少量固定
- 最大値のみ制約
- 出典または検証済みルールにより真のゼロと判断できる場合だけ栄養寄与ゼロとして扱う

欠損、未確認または根拠不足を真のゼロと混同しないこと。根拠がない場合は最適化対象外または不明寄与として扱い、未採用または推計不能の栄養値は`null`のまま維持すること。NutritionAppの正規集計、既知小計および`--.-`表示の仕様は変更しないこと。

## 15. UI要件

### 15.1 推計実行UI

- 欠損栄養素がある場合に「欠損値を推計」操作を表示すること。
- 自動実行設定時はJAN取得後に推計を開始できること。
- 推計中、完了、部分完了、失敗を表示すること。
- UIは日本語とし、iPhone縦画面と片手操作を優先すること。
- 推計操作は食品登録画面の補助導線として配置し、食事登録時のQuick導線、既存食品を3操作以内で記録する目標およびFOODMASTERの既存構成を妨げないこと。
- 推計設定を追加する場合は、設定タブの上位セクション順を変更せず「食品登録」内の補助設定として配置すること。
- 推計中でも食品登録を推計なしで続けられ、既存食品の検索・記録・編集・削除・集計をブロックしないこと。

### 15.2 推計結果UI

各栄養素について以下を表示すること。

- 栄養素名
- 現在値
- 推計値
- 推定範囲
- 信頼度
- 出典
- 推計方法
- 警告
- 採用チェック

画面表示は小数1桁を初期値とし、保存値とJSON/CSVでは必要な精度を保持すること。推計不能な項目は数値をゼロ表示せず、「推計不可」と理由を表示すること。

外部データ取得値には、正確性・完全性を保証しないこと、取得元およびユーザー確認前であることを表示すること。参考推計値には推定範囲と信頼度を常に併記すること。

### 15.3 採用操作

- 栄養素単位で選択できること。
- 一括採用できること。
- 一括不採用できること。
- 既存値は推計値で上書きできないこと。
- 採用後に元へ戻せること。
- 採用、取り消しまたは保存失敗を明確に通知すること。エラーは原因と次に取れる操作を日本語で示すこと。
- 採用または取り消しが保存済み食事記録へ遡及しないことを確認画面で明示すること。

### 15.4 自動採用

現行の正本要件下では実装しない。信頼度、推定範囲または最適化誤差にかかわらず、ユーザーが結果を確認して採用すること。将来検討する場合は、先に正本と設計判断を改定すること。

## 16. 非機能要件

### EST-NFR-001 独立性

推計コアは以下へ依存しないこと。

- IndexedDB
- NutritionAppの画面構造
- JAN読み取りライブラリ
- Open Food Facts固有レスポンス形式

### EST-NFR-002 拡張性

- 食品カテゴリを設定追加で拡張できること。
- 栄養素を追加できること。
- 新しい商品DBや成分DBを追加できること。
- 最適化エンジンを交換できること。

### EST-NFR-003 再現性

- 同一入力、同一モデルバージョン、同一乱数シードで同一結果を再現できること。
- 推計時の設定スナップショットを保存すること。

### EST-NFR-004 追跡可能性

- 推計結果から入力、候補原材料、モデルバージョン、採用判断を追跡できること。
- 栄養素ごとの由来を確認できること。

### EST-NFR-005 性能

初期目標:

- 単一シナリオ推計: 1商品あたり数秒以内
- 複数シナリオ推計: UI操作を阻害しないこと
- NutritionApp側は非同期処理とすること

### EST-NFR-006 オフライン対応

- NutritionAppはPWAとして、初回キャッシュ後に保存済み食品の検索、食事記録、編集、削除、集計および採用済み推計値の参照をオフラインで利用できること。
- 外部API型推計の場合、オフライン時は推計不可を明示すること。
- 推計不可、タイムアウト、API停止または推計機能の無効化によって、食品の手入力登録やNutritionAppの既存機能を失敗させないこと。
- 将来的なブラウザ内推計へ移行できる構造を維持すること。

### EST-NFR-007 セキュリティ

- API利用時はHTTPSを使用すること。
- 不要な個人情報を送信しないこと。
- NutritionAppから外部APIへ送信する情報は原則としてJAN/GTINだけとし、商品名、メーカー、栄養値、原材料、食品ID、食事記録、設定、推計履歴またはその他の個人データを送信しないこと。
- 外部APIアダプターは送信項目を許可リストで検証し、共通推計入力JSONをそのまま送信しないこと。
- APIキーをクライアントコードへ埋め込まないこと。
- 個人の食品データ、推計履歴またはバックアップをGitへコミットしないこと。

### EST-NFR-008 データライセンス

- Open Food Factsなど外部DBのライセンス条件を遵守すること。
- 出典を保存すること。
- 再配布・DB統合時の条件を確認すること。
- 一般食品の参照データは日本食品標準成分表を基礎とし、版、取得日、出典および加工日を保持すること。
- 工業原材料候補、事前分布、配合範囲および加工係数にも出典と版を必須とすること。

### EST-NFR-009 テスト容易性

- 推計コアを単体テスト可能にすること。
- NutritionAppアダプターをモック結果で検証できること。
- 既知値を隠した検証データセットを作成できること。

### EST-NFR-010 日時

- 日時はISO 8601形式で保存すること。
- 日付表示、履歴の日単位絞り込みおよび採用日の判定は`Asia/Tokyo`を基準とすること。
- 推計処理によって食事記録の摂取日時または表示順を変更しないこと。

### EST-NFR-011 医療用途の禁止

- 推計値を診断、治療、個別の食事指導、摂取目標の自動決定または実測値相当の値として使用しないこと。
- 推計結果画面に、推計には誤差と不確実性があり、医療上の判断を行わない旨を表示すること。

## 19. テスト要件

### 19.1 単体テスト

- 原材料文字列の正規化
- 括弧・区切り文字解析
- 原材料順制約
- 候補生成
- 栄養計算
- 推定範囲計算
- 信頼度判定
- 警告生成
- JSONスキーマ検証
- `null`と真の`0`の区別
- 明示換算がない`個`・`袋`・`ml`からgへ変換しないこと
- 推計結果を要求時の基準量・基準単位へ戻す処理

### 19.2 統合テスト

- NutritionApp入力から推計結果まで
- 推計結果から採用値保存まで
- APIエラー時のフォールバック
- 原材料なし商品の処理
- 一部栄養素のみ推計可能な場合
- 採用・取り消し時のIndexedDBトランザクション失敗
- 推計後に食品が編集された場合の競合検出
- 採用・取り消し後も既存食事記録のスナップショットと集計値が変わらないこと
- 推計関連データを含むJSONバックアップ・復元、および不正JSONで既存データが変わらないこと
- 外部APIアダプターがJAN/GTIN以外を送信しないこと
- 推計API停止・オフライン時も保存済み食品の検索、食事記録、編集、削除、集計が利用できること

### 19.3 精度検証

メーカーが対象栄養素を公表している商品を検証用に使用する。特に加工損失の影響を受けやすいビタミンは、栄養素ごとに実値との誤差と推定範囲包含率を確認する。

検証時は対象栄養素を入力から除外し、推計後に実値と比較する。

実商品検証に先立つ回帰評価として、MEXT参照値から作成した人工配合fixtureを使用できる。人工配合では原材料表示順、真の配合比、ラベル表示を模した主要栄養値、対象栄養素の正解値および参照値の`null`を固定し、同じfixtureで変更前後を比較すること。人工配合の結果は内部整合性だけを示し、メーカー公表値による独立検証や実商品の精度保証として扱わないこと。現行評価結果は`docs/analysis/nutrient_estimator_accuracy.md`に記録する。

評価指標候補:

- 平均絶対誤差
- 中央絶対誤差
- 平均絶対パーセント誤差
- 推定範囲内包含率
- 高信頼度判定時の誤差
- 最適化成功率

### 19.4 初期完了基準

- 対象商品の90%以上で最適化が正常終了すること。
- 原材料表示順に矛盾しないこと。
- 極端に非現実的な配合が一定割合未満であること。
- 飽和脂肪酸、食物繊維、カルシウム、鉄、ビタミンA・E・B1・B2・Cについて誤差評価を実施済みであること。
- 推定範囲の包含率を測定できること。
- NutritionApp上で採用・不採用・取り消しが動作すること。
- 保存済み食事記録への非遡及、バックアップ・復元、外部送信項目制限を検証済みであること。

## 21. リスク

### 21.1 原材料の曖昧性

「植物油脂」「乳等を主要原料とする食品」などは、詳細成分を特定できない。

対策:

- 複数候補
- 推定範囲
- 低信頼度
- 警告表示

### 21.2 原材料配合の識別不能

既知栄養値の数に対して原材料候補が多い場合、複数の配合が同程度に適合する。

対策:

- カテゴリ別事前分布
- 配合範囲
- 複数シナリオ
- 単一値ではなく範囲表示

### 21.3 ビタミンの加工損失

ビタミンは製造工程の影響を受けやすい。

対策:

- 栄養素別残存率
- 信頼度低下
- 加工工程不明の警告

### 21.4 外部DBの品質

Open Food Factsはユーザー参加型であり、誤記や古い情報が存在し得る。

対策:

- 取得元と更新情報の保存
- パッケージ画像確認
- ユーザー確認後の採用
- 既存値の直接上書き禁止

### 21.5 ライセンス

外部DBの統合・再配布条件が開発方針へ影響する可能性がある。

対策:

- データソースごとのライセンス記録
- 出典表示
- 利用条件確認

### 21.6 プライバシーと外部サービス停止

推計に必要な商品名、栄養値、原材料等を外部サービスへ送る設計は、正本の「原則バーコード番号のみ送信」と衝突する。また、外部サービス停止時に食品登録まで失敗するとNutritionAppのオフライン方針を損なう。

対策:

- 外部APIへはJAN/GTINだけを送信する
- 全項目を扱う共通入力はローカル、ブラウザ内またはテスト用途に限定する
- 推計を食品登録・食事記録から切り離し、失敗時も手入力と既存機能を継続する
- 外部APIの採否や追加情報送信は本書だけで決定せず、正本を先に改定する

## 22. 判断済み事項

- 推計ツールは自作可能である。
- 最適化アルゴリズムより、食品データ、原材料辞書、カテゴリ別ルールの品質が精度を左右する。
- 既存食品DBを全面再構築せず、工業推計用レイヤーを追加する。
- 設計は広いカテゴリへ拡張可能にし、初期実装は単一カテゴリに絞る。
- NutritionAppとの入出力契約は先に決める。
- 推計コアはNutritionAppから独立させる。
- 初期運用は手動採用とする。
- 自動採用は現行の正本要件下では実装しない。
- 推計値は単一値だけでなく範囲と信頼度を持たせる。
- 栄養素単位で公表値・入力値・推計値の由来を保持する。
- 採用は欠損値だけを対象とし、既存値および保存済み食事記録を変更しない。
- NutritionAppから外部APIへは原則としてJAN/GTINだけを送信する。
- 本機能はNutritionAppのMVP完成後に着手する。

## 24. 受け入れ条件

初期版は以下を満たした時点で受け入れ可能とする。

1. 正本のMVPが完成しており、本機能を無効化・失敗させても既存機能とMVP受け入れ条件を満たせる。
2. NutritionAppからローカル・ブラウザ内連携用の推計要求JSONを生成できる。
3. 外部APIを利用する場合、NutritionAppからJAN/GTIN以外を送信しないことをテストで確認できる。
4. 推計コアがNutritionAppへ依存せず単独実行できる。
5. 初期対象カテゴリの商品で、明示された基準重量がある場合に原材料解析と配合最適化ができる。
6. 飽和脂肪酸、食物繊維、カルシウム、鉄、ビタミンA・E・B1・B2・Cを、参照プロファイルに根拠値が存在する範囲で推計できる。根拠値が欠損する栄養素はゼロ補完せず、部分完了または推計不可として扱う。
7. 推計値、基準量・基準単位、範囲、信頼度、警告を返せる。
8. NutritionApp上で推計結果を参考値として確認できる。
9. 欠損している栄養素だけを対象に、栄養素単位で採用・不採用を選択できる。
10. 採用値へ`nutrientMetadata`を付与できる。
11. 採用前の値とメタデータを保持し、競合がない場合に取り消しできる。
12. 推計要求、結果、判断履歴をIndexedDBへ保存し、採用・取り消しをトランザクションで実行できる。
13. 推計値の採用・取り消し後も、保存済み食事記録の食品スナップショットと計算済み栄養値が変わらない。
14. 推計関連データを含むJSONを出力・復元でき、不正JSONで既存データが変わらない。
15. オフラインまたは推計API停止時も、保存済み食品の検索、食事記録、編集、削除、集計および手入力登録を利用できる。
16. 既知商品を用いた精度検証を実施できる。
17. モデルバージョンごとの再現性を確保できる。
18. 日本語・iPhone縦画面で採用、取り消し、失敗および次に取れる操作を確認できる。
