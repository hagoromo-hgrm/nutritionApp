01 / Search paths

用途の違う検索を、1本に混ぜない

通常の文字検索、MEXT食品の日常語検索、メニュー検索、バーコード検索は、 同じ「検索」に見えても一致条件が異なります。

文字検索

食品検索

一般名、別名、メーカー、読み、正式名称、関連語を採点し、食品グループ単位で返します。

MEXT

日常語グループ検索

「豚肉」「砂糖」などの上位概念を検索し、種類・部位などから成分表グループへ解決します。

メニュー

Myメニュー・一般メニュー・Myセット

メニュー名、分類、別名、構成食品、入れ子メニューをたどって別系統で検索します。

JAN / GTIN

バーコード検索

番号を文字列のまま完全一致で端末内検索します。通常の文字正規化や曖昧一致へ渡しません。

検索の正本は端末内 保存済み食品と検索メタデータはIndexedDBから読み、通常の食品検索はオフラインで完結します。 外部APIはバーコード候補が端末内にない場合の補助です。

食事登録では、通常食品検索にMEXTのユーザー向け検索と各種メニュー検索を加え、 画面上で同じ検索語の候補としてまとめます。ただし、内部の採点方式は検索種別ごとに独立しています。

02 / Pipeline

通常の食品検索は6段階

1. 正規化表記ゆれをそろえる
2. 分類一般 / 市販・外食
3. グループ化一般名ごとにまとめる
4. 採点文字・代表性・履歴
5. 表示代表1件と属性候補
6. 属性選択存在する組合せだけ
食品確定1つのFood ID
分量選択既定量または任意量
選択記録頻度・最終選択時刻
食事へ追加スナップショットを作成

検索結果は既定20件、最大100件のページ単位で返せます。次ページ位置はオフセットを表す カーソルとして扱います。

03 / Normalization

検索前に表記ゆれをそろえる

人が入力した文字列と保存済み名称の両方へ、同じ正規化を適用してから比較します。

処理 目的 例
NFKC 全角・半角などの互換文字をそろえる Ａ → A
小文字化 英字の大小を区別しない COFFEE → coffee
ひらがな化 カタカナとひらがなの差を吸収する タマゴ → たまご
区切り除去 空白、句読点、記号、アンダースコアを無視する ビタミン B-1 → びたみんb1
バーコードは別扱い JAN/GTINは先頭ゼロを含む識別子です。通常の文字正規化へ渡さず、文字列で完全一致します。

04 / Categories

タブは検索後の見た目ではなく、候補集合を決める

タブ 対象 判定
すべて 食品全体。食事登録ではメニュー検索結果も統合可能 分類による除外なし
一般食材 MEXT食品などの一般食品 市販・外食の条件に当てはまらない食品
料理メニュー Myメニュー、一般メニュー、Myセット 食品検索とは別のメニュー検索を使用
外食・市販 商品や外食として登録した食品 isCommercial === true、または有効なバーコードあり

FOODMASTERの一覧・検索には料理メニューを混ぜず、「すべて」「一般食材」「外食・市販」を使います。 食事登録では目的に応じてメニューも同じ検索画面へ統合します。

05 / Grouping

検索結果は食品レコードではなく、一般名のグループ単位

部位や調理状態を持つ全レコードを平坦に並べると、同じ食品名が大量に表示されます。 そこでfoodGroupIdごとにまとめ、結果一覧には代表1件を表示します。

グループ内で行うこと

  1. その分類に含まれる食品を集める
  2. 各バリエーションへ文字一致・利用履歴の点を付ける
  3. 最もよく一致したバリエーションを求める
  4. グループ全体の点数を決める

一覧へ返すもの

  • 一般名を持つFoodGroup
  • 代表として表示するFood
  • 選択可能な全バリエーション
  • 合計点と一致理由
一致した食品と表示代表は同一とは限りません グループの点数は最もよく一致したバリエーションから計算しますが、 表示用食品はdefaultVariantIdがあればそれを優先します。 最終的な食品は、その後の属性選択で確定します。

06 / Text score

文字一致は、自然な名称を最優先する

1つのバリエーションに対し、上から順に一致を判定し、最初に当たった点を使います。 関連語は補助的な一致なので、主要な名称より低く設定されています。

一般名 完全一致100
別名 完全一致95
メーカー 完全一致90
一般名 前方一致80
別名 前方一致75
メーカー 前方一致70
読み 完全一致70
一般名 部分一致60
別名 部分一致55
メーカー / 読み 部分50
正式名称 部分一致40
関連語≤25

関連語は25 × weightです。どの項目にも一致しないグループは、 検索語が空でない限り結果から除外します。

07 / Personalization

文字一致を壊さない範囲で、よく使う食品を上げる

合計 ＝ 文字一致 ＋ 代表性 ＋ 使用頻度・お気に入り ＋ 最近の使用

使用頻度

選択回数にlog2を使って緩やかに加点します。お気に入りは5点を追加し、 合わせて最大25点です。

最近の使用

最終選択直後を15点とし、90日かけて直線的に0点へ減らします。 30日以内は「最近使った」と判定できます。

代表性

FoodGroup.representativeScoreをそのまま加え、 同程度の一致なら一般的なグループを上へ出します。

同点時

合計点、代表性、一般名の日本語順、食品IDの順で安定した並びにします。

08 / Variant resolution

属性選択は、検索後に1つの食品を確定する工程

検索結果の「ご飯」「豚肉」は入口です。種類、部位、調理状態などを選び、 実在する組合せに対応した1つの食品IDを確定します。

グループ選択一般名
候補計算現時点で可能な値
属性選択種類・部位・状態
再整合無効な後続値を解除
一意に解決Food ID / source_id
  • 現在の選択と両立する属性値だけを有効にします。
  • 前の属性変更で成立しなくなった後続選択は、自動的に解除します。
  • 必須属性が不足、値が不正、複数候補が残る場合は、曖昧な食品を推測で保存しません。
  • 画面で非表示にした属性は、食品ごとに設定した既定値で解決します。

09 / MEXT everyday search

MEXTの日常語検索は、専用インデックスを先に使う

成分表の正式名称を直接並べる前に、ユーザー向け食品グループを検索します。 検索結果は上位属性の事前選択を持つことができ、部位などを別結果として展開できます。

一致 点 意味
グループ名の完全一致 600 日常的な親食品名と完全一致
ショートカットの完全一致 550 部位・卵種などの直接入口
グループ名・検索語の完全/前方一致 500 親概念または登録検索語
ショートカットの前方一致 450 属性への近道
その他の部分一致 300 補助的な一致
成分表グループの正式名 200 下位の正確な名称からも到達可能

検索語の正規化はNFKC・小文字化・空白整理を行い、空白を除いた比較も使います。 通常の食品検索より高い点数ですが、これは別の検索経路内での順位であり、 通常検索の100点と直接比較する値ではありません。

10 / Menu search

メニューは構成の中まで検索する

Myメニュー、一般メニュー、Myセットは食品グループではありません。 名前だけでなく、構成食材からも見つけられるように別の探索を行います。

照合する情報

  • メニュー名、カテゴリ、登録別名
  • 構成食品の一般名・正式名称・メーカー・読み
  • 構成食品グループの別名
  • 入れ子になったメニューの構成

安全策

  • 正規化後の部分一致を使用
  • 入れ子を再帰的にたどる
  • 同じメニューを再訪しないよう循環を防ぐ
  • 食品検索結果とはカテゴリに応じて統合

11 / Multiple queries

複数検索バーは、検索ごとの選択状態を保つ

複数の食材を続けて探す場合、入力欄ごとに検索を並列実行し、それぞれの結果と選択状態を分離します。

複数語を入力検索欄ごとに保持
並列検索結果グループを分離
順に選択未選択結果を残す
全件完了最後の選択で確認へ
確認画面早期移動も可能

通常はすべての検索結果から選択されるまで検索画面に留まります。 右上の「確認画面へ」から、未選択の結果を残したまま早く進むこともできます。

12 / Logs & resilience

検索改善用の記録は、選択操作を止めない

どの候補が何位で表示され、何が選ばれたかを端末内へ記録します。 ただし、この補助記録に失敗しても食品選択は成功させます。

SearchLog

入力語、正規化語、処理時間、結果数、候補ごとの順位・点数・一致理由を保持します。

選択結果

選んだグループ・食品・順位・経過時間、または未選択で終わったことを追記します。

FoodUsageStat

食品ごとの選択回数と最終選択日時を更新し、次回の個人向け順位に使います。

失敗時の方針

ログ記録や利用統計更新の失敗は握りつぶし、食事登録の本処理を妨げません。

13 / Walkthrough

「砂糖」と入力した場合を追う

検索語: 砂糖 概念例
  1. 正規化: 表記ゆれを除き、比較用の「砂糖」にします。
  2. 日常語グループ: 上白糖などをまとめるユーザー向け「砂糖」へ完全一致します。
  3. 結果表示: 成分表の正式名称を大量に並べず、一般名「砂糖」を入口として見せます。
  4. 種類選択: 上白糖、グラニュー糖など、存在する候補から選びます。
  5. 食品確定: 選択に対応する成分表グループと食品レコードを一意に解決します。
  6. 分量入力: g、小さじなど、明示済み換算のある単位で入力します。
  7. 記録: 一般名を表示用に保ちつつ、確定食品の栄養値をスナップショットへ保存します。
ここで示したのは処理の考え方です 実際に表示される種類や既定値は、生成済みMEXTデータとユーザー設定に従います。

実装を確認したい場合

  • 通常食品検索 — foodSearch.ts
  • タブ分類 — foodClassification.ts
  • MEXT日常語検索 — mextUserFoodData.ts
  • MEXT属性解決 — mextFoodData.ts
  • 選択肢の制約 — variantConstraints.ts
  • 検索データ読込・ログ — db.ts

14 / Current boundaries

実装済みの範囲と、まだ順位に使っていない情報

データ型に存在する項目が、すべて現在の順位計算へ使われているとは限りません。 既存の将来向け設計資料と、現在動いている処理を区別するための一覧です。

現在の順位には未使用

  • FoodAlias.priority
  • FoodAlias.aliasType
  • 保存済みのnormalizedAlias
  • 他ユーザーを含む全体利用頻度

別名は検索時に再正規化し、現在は同じ重みで評価します。

現在の処理上の境界

  • 候補はIndexedDBの全文索引ではなく、読込後にメモリ上で採点
  • メニューは食品と共通の点数表では順位付けしない
  • 「最近使った食品」は検索ログではなく食事記録から生成
  • 選択回数は検索結果から食品を開いた時点で更新
将来案を現行仕様として読まない 既存の食品検索設計文書には将来要件も含まれます。 デバウンス、全体利用頻度、別名優先度、大量データ向け索引検索などは、 このガイドでは現在実装済みとして扱っていません。
