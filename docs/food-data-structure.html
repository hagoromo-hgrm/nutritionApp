01 / Overview

まず、食品データは5つに分けて考える

食品本体は栄養計算の中心ですが、それだけでは自然な検索や過去記録の保全ができません。 検索用データと食事用データを分離することで、それぞれを安全に更新できます。

出典データ MEXT・商品表示・ユーザー入力
Food 基準量・栄養値・出所
検索メタデータ 一般名・別名・グループ・属性
メニュー 食品と分量の再利用可能な構成
食事記録 登録時点の値を固定した複製
14食品ごとに保持する栄養項目
4食品の出所区分
100gMEXT食品が維持する栄養価の基準
null ≠ 0不明とゼロを明確に区別
この文書の位置づけ 現在の実装を理解するための案内です。要件の正本は requirements.md、重要な設計判断は decisions.mdです。

02 / Core entity

食品本体 Food

Foodは「栄養計算できる1つの確定した食品」です。同じ一般名で呼ばれる食品でも、 部位・調理状態・商品が異なれば別レコードになります。

まとまり 主なフィールド 役割
識別 id 食品を一意に参照するためのID。表示名を変更しても同じ食品として扱います。
名称 name / officialName / displayName / reading 元レコード名、正式名称、一般向け表示名、読みを目的別に分けます。
商品識別 maker / barcode / isCommercial メーカー、JAN/GTIN、市販・外食区分を保持します。バーコードは数値ではなく文字列です。
出所 source / sourceVersion どこから来た値か、どの版かを追跡します。
栄養基準 baseAmount / baseUnit 栄養値が「何量あたり」かを定義します。
入力初期値 servingAmount / servingUnit 食事登録で最初に提示する、普段使いやすい分量と単位です。
単位換算 inputUnitConversions[] 「1個は基準量の何単位か」のような、明示済みの換算だけを保持します。
検索・分類 foodGroupId / variantAttributes 一般名のグループと、その中の部位・状態などを結びます。
栄養値 nutrients / nutrientMetadata 14栄養素の値と、必要に応じて各値の由来・推計情報を保持します。
推計補助 ingredientsText / estimationReferenceMassG / estimatorGenreId 市販食品の欠損栄養素を推計するときの根拠です。食品検索の分類とは分離されています。 
{
  "id": "mext:...",
  "displayName": "ご飯",
  "officialName": "水稲精白米 ごはん",
  "source": "mext",
  "baseAmount": 100,
  "baseUnit": "g",
  "servingAmount": 1,
  "servingUnit": "杯",
  "inputUnitConversions": [{ "unit": "杯", "baseAmount": 150 }],
  "nutrients": { "energyKcal": 156, "...": null }
}

上は構造を説明するための簡略例です。実データの値やIDを保証するサンプルではありません。

03 / Names

名前は「正しさ」と「自然さ」を分担する

成分表の正式名称は確認に必要ですが、日々の記録では「ご飯」「砂糖」のような一般名の方が自然です。 そのため、1つの名前をすべての画面へ流用しません。

食品マスター側

  • name: 元データまたは食品レコードの基本名
  • officialName: 出典に沿った正式名称
  • displayName: ユーザーが認識しやすい表示名
  • FoodGroup.displayName: 検索結果をまとめる一般名

食事記録側

  • FoodSnapshot.userFacingName: 選択入口で見えていた一般名
  • 食事内訳や確認画面は、この一般名を優先
  • 正式名称は属性選択中の確認材料として使用
  • 後日の改名で過去記録の表示を変えない
同じ文字列を保存しているだけではありません 「検索で見た名前」と「最終的に栄養計算へ使う食品」は別の役割です。 一般名から属性を選び、最後に確定した食品レコードへ到達します。

04 / Search metadata

グループ、別名、関連語、バリエーション

自然な検索を成立させるための情報は、栄養値を持つFoodから分けて保存します。 これにより、検索語を追加しても栄養値そのものを書き換えずに済みます。

G

FoodGroup

検索結果に1件として見せるまとまりです。一般名、読み、分類、既定の代表食品、 代表性スコア、有効状態を持ちます。

A

FoodAlias

同義語、読み、略称です。グループ全体または特定バリエーションへ結び付けられます。 保存時には正規化済み文字列も保持します。

R

FoodRelatedTerm

完全な別名ではないものの、検索の手掛かりになる語です。 0〜1の重みを持ち、別名より弱い一致として扱われます。

V

FoodVariantAttributes

種類、部位、栽培、原料豆、皮、調理、加工、品種、名称補足など、 同じ一般名の中で食品を区別する属性です。

一般名例: 豚肉
グループ検索結果のまとまり
属性部位・調理状態など
バリエーション存在する組合せだけ
Food栄養計算する実体

05 / MEXT layers

MEXT食品は「日常語」と「成分表」を2階層でつなぐ

日本食品標準成分表の分類は栄養データの正確な参照に必要です。一方で、検索入口は日常語であるべきです。 そこで、上位のユーザー向けグループと、下位の確定済み成分表グループを分離しています。

ユーザー向け層
日常的な食品名と、種類・部位などの上位選択肢
成分表グループ層
確定済みの食品グループと、調理・皮・品種などの選択可能属性
出典レコード層
MEXT source_idで特定される、可食部100gあたりの食品レコード
1,399ユーザー向け食品グループ
1,494確定済みMEXT食品グループ
2,538MEXT食品バリエーション
3層日常語・成分表グループ・出典レコード
概念的な選択例 一般名 → 実体

ご飯 → 種類「白ごはん」 → 原料「うるちまい」 → 対応する成分表グループ → 属性に一致する食品レコード

上位選択で決まらないものだけを下位属性で選びます。存在しない組合せは候補から外し、 先の選択によって無効になった後続値は調整されます。

生成済みMEXTデータはdata/mext/app/にあり、UIはJSONを直接走査せず、 mextUserFoodData.tsとmextFoodData.tsを通して参照します。

06 / Amounts & units

栄養価の基準と、普段入力する単位は別

成分表の100g基準を「1杯」へ置き換えるのではなく、栄養値の基準は維持したまま、 入力しやすい単位への換算を追加します。

値 意味 例
baseAmount / baseUnit 登録済み栄養価が対応する基準量 100 g
servingAmount / servingUnit 食事入力で優先する既定分量 1 杯
inputUnitConversions 1入力単位が基準単位で何量か 1 杯 = 150 g
摂取栄養値 ＝ 基準量あたりの栄養値 × 換算後の摂取量 ÷ 基準量
  • 基準単位と同じ単位は、そのまま計算できます。
  • 異なる単位は、食品に明示登録された換算がある場合だけ計算できます。
  • 「個」「杯」「袋」などのユーザー定義単位を、名前だけでgへ推測しません。
  • MEXT食品は可食部100g基準を維持し、日常単位は別フィールドへ持ちます。

07 / Nutrients

14栄養素と「分からない」の扱い

すべての栄養素は数値またはnullです。nullは未収載・未入力などの欠損であり、 0ではありません。

  • エネルギー kcal
  • たんぱく質 g
  • 脂質 g
  • 炭水化物 g
  • 食物繊維 g
  • 食塩相当量 g
  • カルシウム mg
  • 鉄 mg
  • ビタミンA μg
  • ビタミンE mg
  • ビタミンB1 mg
  • ビタミンB2 mg
  • ビタミンC mg
  • 飽和脂肪酸 g

nutrients

計算に使う値です。出典に数値がなければnullを維持します。 単位換算後も、元がnullなら結果はnullです。

nutrientMetadata

メーカー表示、外部情報、ユーザー入力、推計、導出などの由来と、 推計時の信頼度・範囲・手法を栄養素ごとに保持できます。

08 / Historical integrity

食事へ登録した瞬間に、必要な値を複製する

食事記録は食品IDだけを参照し続けません。登録時点の名称、基準量、換算、栄養値を FoodSnapshotへコピーします。

Food現在のマスター
分量入力amount + unit
栄養計算calculatedNutrients
FoodSnapshot登録時点を固定
MealEntry日時・区分・順序と保存

食品マスターを後で編集した場合

新しい記録には更新後の値を使えますが、過去記録の栄養集計は勝手に変わりません。

食品マスターを削除した場合

食事記録は残り、スナップショットを使って表示できます。削除済みであることも保持できます。

Myメニューを食事へ追加した場合

構成食材を再帰的に複製したMealMenuSnapshotを持ち、その食事だけのアレンジを保存します。

Myセットの場合

メニュー参照に加え、確定した食品ID・分量・単位をfoodItemsとして一括登録に使います。

09 / Provenance

4つの出所を同じ形へそろえる

保存後は同じFoodとして扱いますが、正確性や再配布条件が異なるため、 sourceと版情報は失いません。

source 用途 扱い
mext 日本食品標準成分表の一般食品 食品番号を保ち、可食部100g基準で変換。欠損はゼロ補完しません。
user ユーザーが登録・編集した食品 パッケージ表示または入力内容を正として端末内に保存します。
imported 事前検証済みDBからの食品 元ファイルを直接同梱せず、検証・正規化した生成物だけを投入します。
open_food_facts バーコード検索で得る補助候補 ユーザー確認後に保存します。外部情報を無条件の正解として扱いません。
市販・外食の判定 isCommercialが明示的に有効、または有効なバーコードを持つ食品を 「外食・市販」として分類します。食品成分の出所区分とは別の軸です。

現在のimported生成物は、ユーザー提供DB 255件を検証し、 基準量と栄養値を持たない名称候補を除いた144件を採用しています。 採否基準と再生成方法はimported食品データの説明に記録しています。

10 / Storage & backup

端末内のIndexedDBを正本にする

実行時データはDexie.jsを通してIndexedDBへ保存します。アプリ更新時の初期食品投入と、 ユーザーが作ったデータの保存を区別しています。

食品・記録

foods、meal_entries、favorites、settings

メニュー

menus、general_menus、menu_sets

検索

food_groups、food_aliases、food_related_terms、利用統計、検索ログ

栄養推計

推計リクエスト、結果、採否、設定、未解決原材料統計を別テーブルで管理します。

JSONバックアップは食品、食事記録、設定、お気に入り、検索メタデータ、Myメニュー、 一般メニュー、Myセット、推計関連データを含みます。復元では形式検証後に1つの トランザクションで入れ替え、検索メタデータを再整合します。

11 / Reading checklist

構造を読むときの5つの要点

  1. 一般名は食品そのものではない。 グループと属性を経て、栄養値を持つ食品へ到達します。
  2. 既定入力分量は栄養価の基準を変えない。 入力しやすくする別レイヤーです。
  3. nullは0ではない。 欠損を隠さず、集計でも区別します。
  4. メニューは再利用する構成、食事は固定した記録。 食事ごとの編集は原本へ戻りません。
  5. 出所と分類は別。 MEXTかユーザー入力かと、一般食品か市販・外食かは独立しています。
