# 食事記録で入力用単位からgへ変更できない問題の調査

- 調査日: 2026-10-07
- 調査対象: `13053d6` の実装、`4152add` と周辺の履歴
- ユーザー確認済み症状: gを選んでも元の単位に戻る
- 作業範囲: 原因・履歴・検証範囲の調査。アプリの修正は行っていない。

## 結論

MEXT由来の種類・属性選択画面で食品を新規記録すると、単位変更をきっかけに初期化処理が再実行され、選んだ単位が食品の既定入力単位へ戻る。gへの換算情報がないためではなく、Reactの状態更新を初期化処理が上書きする不具合である。

この処理は `558abcc`（2026-07-23）で食事編集へ対応した際に導入され、`4152add` の前後でも変更されず残っている。以前の修正後に同じ箇所が再び壊れたという履歴ではない。

以前の依頼内容・当時の操作確認の詳細はGitからは確認できない。以下の「修正が残った要因」は、実際の変更対象とテストから判断できる範囲を記載する。

## 現在の原因

対象: [`src/components/FoodVariantPicker.tsx`](../../src/components/FoodVariantPicker.tsx) の `MextFoodVariantPickerModal`、228～238行。

```tsx
const editingAmount = initialAmount !== undefined
useEffect(() => {
  if (!editingAmount) {
    setAmount(selectedFoodDefaultAmount)
    setAmountUnit(selectedFoodDefaultUnit)
    return
  }
  if (selectedFood && !getFoodQuantityUnits(selectedFood).includes(amountUnit)) {
    setAmountUnit(selectedFoodDefaultUnit)
  }
}, [amountUnit, editingAmount, selectedFood,
    selectedFoodDefaultAmount, selectedFoodDefaultUnit, selectedFoodId])
```

1. 新規登録では `initialAmount` が渡されず、`editingAmount` はfalseになる。
2. 単位選択の `onChange` が `amountUnit` をgへ変更する。
3. `amountUnit` がeffectの依存に含まれるため、effectが再実行される。
4. 新規登録用の分岐で、量と単位を既定値へ無条件に戻す。
5. 既定単位が杯・個等の場合、gが選択状態として残らない。g以外の既定値と異なる登録済み単位でも同じことが起きる。

同じ分岐で `amount` も初期化するため、単位変更時には変更済みの分量も既定値へ戻すコードになっている。

既存食事の編集では [`src/App.tsx`](../../src/App.tsx) の1778～1791行で `initialAmount` / `initialAmountUnit` を渡すため、別分岐に入り、有効なgは維持される。

## 「場合がある」となる理由

食品選択は同じ画面・同じ処理に統一されていない。

| 経路 | 処理 | gへの変更 |
| --- | --- | --- |
| MEXTまたは上位の一般名検索から種類・属性を選び、新規記録 | `MextFoodVariantPickerModal`、初期分量なし | 選択後に既定単位へ戻る |
| 同じ選択画面で既存記録を編集 | 同コンポーネント、初期分量あり | 有効なgを維持する |
| 通常の手動食品familyの選択画面で新規記録 | `LegacyFoodVariantPickerModal` | 食品IDが変わった時だけ初期化するため、gを維持する |
| 通常の食事分量入力画面 | `MealModal` | 同じ単位変更時の初期化処理がない |

分岐は `FoodVariantPickerModal` の53～59行、Legacy側の食品IDガードは335～341行。検索から種類選択へ進むか分量画面へ直接進むかは `App.tsx` の1245～1302行で決まる。MEXT食品すべて・すべての追加導線で必ず発生するわけではない。

なお、基準単位がgでなくg換算も未登録の食品では、gを候補へ出さないのが仕様である。今回確認された「gを選んでも戻る」とは別の条件である。候補生成と栄養計算は [`src/services/nutrition.ts`](../../src/services/nutrition.ts) の9～30行にある。

## 以前の修正で残った要因

### 1. 単位に関する別々の問題を扱い、今回の状態初期化には手が入っていない

周辺の修正は、保存済み属性の再編集、参照中の換算保護、複数換算の保持をそれぞれ改善した。今回の原因であるMEXT新規入力のeffectは変更していない。commit名の「preserve units」だけでは、入力操作の保持まで修正したとは判断できない。

### 2. 新規／編集とMEXT／通常familyの分岐を横断した確認がない

`d4e268b` はLegacy側の初期化を食品ID変更時に限定したが、MEXT側へ同じ対策を適用していない。既存編集は `editingAmount=true` となり、今回の新規登録用分岐を通らない。片方の画面や編集だけを確認すると問題が見えない構造になっていた。

### 3. テストが換算データ・計算・編集開始時の値へ偏っている

- `4152add` の食品単位テストは `foodToDraft` による複数換算保持を確認する。現在の [`tests/food-estimation-draft.test.ts`](../../tests/food-estimation-draft.test.ts) の62行。
- メニュー単位関連テストはセット展開、栄養計算、スナップショットが対象。
- `d4e268b` のUIテストは「手動familyの既存食事」でLegacy側を通り、最初からgの初期値を確認する。現在の [`tests/app-food-search.test.tsx`](../../tests/app-food-search.test.tsx) の243行。
- これらの追加テストには「MEXTの新規記録で、既定入力単位からgへselectのchangeイベントを発火し、その後もgが残る」確認がない。

テストが通ることと、今回の単位操作が直ることが結び付いていなかった。人が実際にどの画面を操作したか、当時の依頼をどう解釈したかは、履歴だけから断定できない。

## 再現・検証

個人データや実端末のIndexedDBには触れず、Reactコンポーネントをjsdomに描画し、単位selectのDOM `change` イベントを発火した。一時的な調査用テストは実行後に削除した。

使用データ: 同梱食品 `mext_01085`（こめ／水稲めし／玄米）。基準100g、既定1杯、明示換算1杯=140g。食品グループIDは既存のMEXT source対応表から付与した。

| 確認 | 観測結果 |
| --- | --- |
| MEXT種類選択で新規入力、杯からgへ変更 | 杯へ戻ることを再現 |
| 「玄米」検索の上位グループ「ご飯」から新規入力、杯からgへ変更 | 杯へ戻ることを再現 |
| MEXTの既存記録編集、杯からgへ変更 | gを維持 |
| 合成した通常familyの新規入力、杯からgへ変更 | gを維持 |
| 食品の候補単位と栄養計算 | 候補はg・杯。140gと1杯の計算結果が一致 |

調査用5件の観測確認に加え、既存の `nutrition`、`food-estimation-draft`、`meal-menu-snapshots`、`menu-set-meals` テストを実行し、合計57件が通過した。調査用テストの成功は不具合の観測結果が一致したことを意味し、修正完了を意味しない。実機Safariの操作確認は行っていない。

## 修正時に必要な対応

- 初期分量の設定、食品を変更した時の初期化、使用中単位が使えなくなった時の補正を分離する。
- 同じ食品で有効な入力単位を変更しただけの場合は、既定値で上書きしない。
- MEXTと通常family、新規と編集、上位一般名検索と直接グループ選択をそれぞれ確認する。
- 既定単位が杯・個等の食品でgへ変更し、再描画後の選択・分量・保存されたスナップショットまで確認する回帰テストを追加する。
- 食品種類・属性の変更時の分量方針も確認する。単位変更時に数値自体を換算するかは今回の原因とは別の仕様判断であり、意図せず追加変更しない。

今回の原因への対処に食品DBの再投入や既存食事の書換えは必要ない。
