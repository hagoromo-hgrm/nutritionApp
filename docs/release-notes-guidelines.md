# リリースノート記述規約

- 文書状態: 評価待ち
- 策定日: 2026-09-14
- 対象: Nutrition PWAの利用者向けリリースノート

## 1. 目的

リリースノートは、アプリを更新した利用者が「何が変わったか」「自分の記録に影響するか」「何か操作が必要か」を短時間で判断するために書く。

開発作業の一覧やコミットログの要約にはしない。仕様の正本は [`requirements.md`](requirements.md)、設計判断と廃止した方針は [`decisions.md`](decisions.md)、開発手順は [`AGENTS.md`](../AGENTS.md) に置き、リリースノートから仕様を新設・変更しない。

本書は文章、保存形式、公開判定に必要な最小限の解析規則を定める。アプリ内の一覧・既読管理・通知・画面遷移などの機能仕様は、実装時に `requirements.md` へ別途定める。

## 2. 対象読者と言語

- 主な読者は、iPhoneのホーム画面から本アプリを使う利用者とする。
- 本文は日本語で書き、内部の型名、関数名、ファイル名、データベース用語を前提知識にしない。
- 画面名やボタン名は、実際の日本語UIと同じ表記を `「」` で示す。
- 医療的な効果、診断、治療、個別の栄養指導と受け取れる表現は使用しない。

## 3. 保存場所と公開単位

実際のリリースノート機能を実装するときは、次の構成を正とする。

```text
docs/releases/
├── unreleased.md
├── v0.2.0.md
└── v0.2.1.md
```

- 開発中の記述は `docs/releases/unreleased.md` に置く。未公開の内容を版付きファイルへ記載しない。
- 公開時に、対象項目を `docs/releases/vX.Y.Z.md` へ移す。1ファイルを1回の本番公開に対応させる。
- `package.json` の `version` をアプリバージョンの正本とする。ビルド時はこの値を配信物のバージョン表示へ埋め込み、別の場所へ同じ値を手入力しない。
- 正規化したバージョンは `0.2.0` のように `v` を含めない。版付きファイル名とGitタグだけ先頭に `v` を付け、それぞれ `v0.2.0.md`、`v0.2.0` とする。比較時はこの接頭辞を除いた値を `package.json` と照合する。
- 公開日は、実装日やマージ日ではなく、本番で利用可能になった `Asia/Tokyo` の日付とする。
- 公開後の版付きノートは履歴として扱う。誤記訂正以外では書き換えず、後続変更は新しい版へ記載する。

`unreleased.md` はフロントマターを持たず、先頭を `# 未公開` とする。その下では5.2節の見出しだけを同じ順序で使用する。項目がない見出しは省略し、全項目を公開版へ移した後もファイルは削除せず、`# 未公開` だけを残す。次回以降へ見送った項目はそのまま残す。アプリと公開ノートのビルド処理はファイル名で `unreleased.md` を除外する。

## 4. バージョンの付け方

バージョンは `X.Y.Z` の3要素で管理する。

- `X`（メジャー）: データ、操作、対応環境などに大きな非互換がある変更
- `Y`（マイナー）: 後方互換のある機能追加や、利用方法が広がる変更
- `Z`（パッチ）: 後方互換のある不具合修正や小規模な改善

`0.x` の開発段階でも、非互換変更を通常の改善として隠さない。`Y` を上げ、リリースノートの「重要なお知らせ」と「データ・互換性」の両方で影響と必要な操作を明記する。IndexedDBのスキーマ番号、JSONバックアップのデータ形式番号、食品データや推計モデルの版はアプリのリリース番号とは別に管理し、変更した場合だけリリースノートへ併記する。

## 5. 1リリースの固定書式

版付きファイルは次の形で書く。フロントマターの3項目は必須とし、将来のアプリ表示で機械的に読み取れるよう、キー名と日付形式を変更しない。

```markdown
---
version: "0.2.0"
releaseDate: "2026-09-20"
summary: "食事登録と履歴確認を、より少ない操作で行えるようになりました。"
---

# バージョン0.2.0

## 重要なお知らせ

- **バックアップ**: 更新前に「設定」からJSONバックアップを保存してください。旧形式からの復元条件は「データ・互換性」を確認してください。

## 新機能

- **Myメニュー**: メニュー全体の単位を「食」以外の「個」「皿」などでも登録できるようになりました。

## 改善

- **食品登録**: 食品に登録済みの入力単位を、編集画面から変更・削除できるようになりました。

## 不具合修正

- **栄養目標**: 身体情報を更新しても、過去の日付には当時の目標量が表示されるよう修正しました。

## 仕様変更

- **食事区分の確認**: 画面上部の「今日の記録へ」を廃止し、画面下部の完了操作へ統一しました。

## データ・互換性

- 既存の食事記録は変更されません。更新後も、登録時点の食品名・栄養値・目標量を表示します。
- JSONバックアップ形式5を引き続き復元できます。更新前の追加操作は不要です。

## 既知の問題

- **PWA更新**: 更新内容が表示されない場合があります。その場合は通信できる状態でアプリを閉じ、再度開いてください。
```

### 5.1 機械可読部分の規則

- フロントマターはファイル先頭に1つだけ置き、`version`、`releaseDate`、`summary` 以外のキーを使用しない。キーの重複を禁止する。
- 3つの値はすべて二重引用符で囲んだ1行の文字列とする。値内で二重引用符が必要な場合は `\"` と記述する。
- `version` はプレリリース名やビルド情報を付けない `0|[1-9][0-9]*` の3要素とし、正規表現では `^(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)$` に一致させる。
- `releaseDate` は実在する日付を `YYYY-MM-DD` で記述する。
- `summary` は改行を含まない20文字以上120文字以内の日本語とし、主要な変更または更新の目的を1文で示す。
- 本文にはH1を1つだけ置き、`# バージョンX.Y.Z` の数値をフロントマターと一致させる。
- 分類見出しはH2だけを使用し、5.2節に定める名前と順序に限る。各見出しには1つ以上の `- ` で始まる箇条書きを置く。
- 本文で使用できるMarkdownは見出し、箇条書き、太字、インラインコード、通常の段落に限る。表、画像、HTML、脚注、外部リンクは使用しない。
- 同じ `version` のファイル、形式不正なファイル、`package.json` と対象版が一致しないリリース用ビルドは失敗させる。不正なノートを無視して配信しない。
- アプリでは版を新しい順に表示する。ノートはビルド時に検証・変換し、アプリ起動時にMarkdown解析失敗が起きる構成にしない。

### 5.2 見出しの順序

見出しは次の順序に固定し、該当項目がない見出しは省略する。

1. 重要なお知らせ
2. 新機能
3. 改善
4. 不具合修正
5. 仕様変更
6. データ・互換性
7. 既知の問題

破壊的変更、更新前のバックアップ、再設定、利用停止を伴う内容は「重要なお知らせ」の先頭へ置く。「仕様変更」は意図して従来動作を変える場合に使い、「不具合修正」は定められた仕様へ戻す場合に使う。機能の廃止や削除は「仕様変更」に記載し、影響が大きい場合は「重要なお知らせ」にも記載する。

## 6. 本文の書き方

### 6.1 1項目の構造

各項目は原則として1つの変更だけを扱い、次の順で書く。

```text
- **対象画面・機能**: 何が変わったか。誰にどのような影響があるか。必要な操作: 利用者が行う操作。
```

- 先頭に対象画面または機能を示す。
- 最初の文で、利用者が確認できる変化を具体的に述べる。
- 対象者や発生条件が限られる場合は、「○○の場合」のように条件を明記する。
- 利用者の操作が必要な場合だけ `必要な操作:` を付ける。操作不要の場合は原則として書かない。
- 1項目が3文を超える場合は分割を検討する。ただし、変更とそのデータ影響は分離しない。

### 6.2 表現

- 「できるようになりました」「表示されるよう修正しました」など、利用者が確認できる結果を先に書く。
- 「一部を改善しました」「最適化しました」「対応しました」だけで終えず、対象と変化を明記する。
- 内部実装だけの説明を避ける。必要な技術用語には、利用者への意味を続けて書く。
- 誇張表現、評価根拠のない「高速」「安全」「完全」、感情的な宣伝文句を使用しない。
- 将来の予定、検討中の案、未実装の内容を、完了した変更と同じ箇条書きに含めない。
- 不具合は、影響範囲を確認できていない限り「すべての利用者に発生した」と断定しない。
- 既知の問題には発生条件と回避手段を書く。確定していない修正日を約束しない。

## 7. 掲載する変更・掲載しない変更

### 7.1 必ず掲載する変更

- 新しい画面、操作、設定、データ出力など、利用者が直接使える機能
- 既存の操作手順、表示内容、初期値、計算結果が変わる変更
- 利用者が遭遇し得る不具合の修正
- 機能、設定、対応環境、外部APIの廃止または制限
- IndexedDB、JSONバックアップ、CSV、食品データ、目標量履歴、食事スナップショットへ影響する変更
- PWAキャッシュ、オフライン利用、iPhone Safariでの更新方法へ影響する変更
- 個人データ、外部送信、ライセンス、データ出典、安全性に関する変更

### 7.2 原則として掲載しない変更

- 利用者から見た動作が変わらないリファクタリング
- テスト、開発用スクリプト、コメント、型だけの変更
- 利用者への影響がない依存関係やビルド設定の更新
- コミットID、ファイル名、関数名の羅列

内部変更でも、性能、安定性、オフライン動作、対応ブラウザー、データ互換性に観測可能な影響がある場合は掲載する。

## 8. データ・互換性の必須確認

データへ触れるリリースでは、次の各点を確認し、該当する内容を「重要なお知らせ」または「データ・互換性」へ具体的に書く。

- 既存の食品、食事記録、設定、体重履歴、目標量履歴、お気に入り、Myメニュー、一般メニュー、Myセットを保持できるか
- 保存済みの食事スナップショットや過去の目標量へ、変更が遡及するかしないか
- IndexedDBの自動移行があるか、移行失敗時に既存データを変更しないか
- 更新前のJSONバックアップが必要か
- 旧JSONバックアップを復元できる範囲と、復元できない版
- CSVの列、精度、文字コード、取り込み可否が変わるか
- 初期食品データの追加・更新・削除が、手動登録食品や削除済み食品へ与える影響
- Service Workerやキャッシュ更新のために、再読み込みやアプリの再起動が必要か

「互換性があります」「データに影響します」だけでは不十分とする。対象データ、更新後の結果、利用者に必要な操作を記載する。

## 9. セキュリティ・個人情報・外部データ

- 個人の食事内容、身体情報、バーコード、バックアップ内容、端末情報を実例として掲載しない。
- 脆弱性修正は、利用者が更新の必要性を判断できる範囲で影響と対処を説明し、悪用を容易にする詳細は公開前に記載しない。
- 外部APIの利用範囲や送信情報が変わる場合は、送る情報、利用条件、オフライン時の挙動を記載する。
- 食品データや推計データの出典・版・ライセンス条件が変わる場合は、対象範囲と注意事項を記載する。

## 10. 作成から公開まで

1. 利用者に見える変更を実装した作業では、対応する `unreleased.md` の追記を実装と同じ作業区切りのcommitに含める。ノートだけの訂正は独立した作業区切りとしてcommitする。
2. コミット差分、テスト結果、要件、ADRを確認し、リリースノートだけが先行していないことを確認する。
3. リリース対象を確定し、未公開項目を版付きファイルへ移す。
4. バージョン、公開日、要約、見出し順、データ影響、必要な操作をレビューする。
5. 本番配信とGitタグの作成後、その版がアプリのリリースノート一覧に表示されることを確認する。
6. 配信を取り消しても版付きノートは削除せず、「重要なお知らせ」の先頭に公開停止の事実、影響する版、利用者の対応を追記する。

コミットログ、Issue、要件、ADRは内部レビューの材料として使用できるが、利用者向け本文へリンクや識別子を掲載せず、そのまま転記しない。リリースノートの公開状態は、commitやpushではなく本番で利用可能になったかどうかで判断する。commit、push、本番配信は [`AGENTS.md`](../AGENTS.md) の権限と手順に従い、リリースノート作成を理由に自動でpushまたは配信しない。

最初の正式リリースも同じ手順で版を決め、そのリリースのコミットにだけ新しいタグを付ける。実際に公開していない過去コミットへ、リリース履歴を整える目的だけでタグや版付きノートを遡及作成しない。

## 11. 既知の問題の扱い

- 新しく判明した問題または当該版の更新判断に影響する問題だけを記載する。
- 一時的な不具合は発生条件と回避手段を記載する。仕様として残る制限は「仕様変更」または「重要なお知らせ」に記載する。
- 問題が解消した版では「不具合修正」へ記載し、過去の版付きノートから元の記述を削除しない。
- 既知の問題がない場合は見出し自体を省略する。

## 12. 良い例と避ける例

良い例:

```markdown
- **食品登録**: 「じゃがいも 塊茎 皮なし 生」など、既存の入力用単位を編集画面から変更できるようになりました。
- **目標量**: 身体情報を更新した日以降だけ新しい目標量を適用し、過去の日付には当時の目標量を表示します。
- **バックアップ**: JSONバックアップ形式を5へ更新しました。形式1から4も引き続き復元でき、更新前の追加操作は不要です。
```

避ける例:

```markdown
- 単位周りを改善しました。
- DBをv12へ変更。
- App.tsxを修正しました。
- いくつかの不具合に対応しました。
```

避ける理由は、対象、利用者が確認できる変化、互換性、必要な操作が判断できないためである。

## 13. 公開前チェックリスト

- [ ] 版付きノートには本番配信される変更だけが含まれている
- [ ] ファイル名、フロントマター、`package.json`、Gitタグ、配信物のバージョンが一致している
- [ ] `v` 接頭辞を除いたバージョンが正規化後に一致している
- [ ] 公開日は `Asia/Tokyo` で実際に利用可能になった日である
- [ ] 要約だけで主要な変更が分かり、誇張や未実装の予定が含まれていない
- [ ] 見出し順が固定され、空の見出しがない
- [ ] 各項目に対象と具体的な変化が書かれている
- [ ] 必要な利用者操作、対象条件、回避策がある場合は明記されている
- [ ] 既存データ、過去記録、バックアップ、CSV、オフラインキャッシュへの影響を確認した
- [ ] UIの名称とリリースノートの表記が一致している
- [ ] 個人データ、秘密情報、未公開の脆弱性詳細が含まれていない
- [ ] `requirements.md` と `decisions.md` の内容に矛盾していない
- [ ] iPhoneの縦画面で読みやすい長さになっている
- [ ] `unreleased.md` が公開一覧へ含まれていない
- [ ] 全ノートが規定のMarkdownとして検証・変換できる
